# 点餐诉求准确性实测

测试日期：2026-10-25。结论：点名餐品的诉求没有进入组合选择约束；否定关键词会反向加分；AI 判词还会虚构替换理由。问题可在本地和线上稳定复现。

## 测试条件和证据

- 线上地址：`https://mccourt.vercel.app/api/recommend`，两次真实请求，共 8 位测试参与者（含 1 位空白诉求对照），每人预算 60 元、饥饿程度 3、无额外标签。
- 测试地点选用上海人民广场，实际返回麦当劳上海黄浦华旭国际大厦餐厅，门店代码 `1450713`。这是测试选址，不代表用户当前位置。
- 官方 MCP 实时返回 117 项餐品。板烧鸡腿堡 23.5 元、雪碧 9.5 元、麦香鱼 22.5 元、可乐 9.5 元均出现在标准化菜单中。
- 板烧鸡腿堡与雪碧合计 33 元；加上脆薯饼 8.5 元后合计 41.5 元，两种组合都在预算内。因此本次漏选不能归因于预算不足或菜单缺少这些餐品。
- 本地真实 API 另测 4 位参与者，结果与线上对应案例一致。用同一份实时菜单直接执行现有组合引擎，共测 12 种输入；另执行一次真实自定义上诉。
- 线上和本地 API 都返回 `judge.engine = openrouter`、`judge.model = qwen/qwen3.7-flash:nitro`，本次不是未配置 AI 或 AI 失败回退。

原始证据：[实时菜单、本地接口、12 个规则案例和上诉](./request-diagnostics.json)、[线上输入和完整返回](./online-request-diagnostics.json)。保存时已移除下单许可。

## 原因与代码证据

### 1. 实际选餐是固定规则，点名需求未被解析

`app/api/recommend/route.ts:16` 先调用 `recommend` 决定餐品，随后才在第 23 行调用 AI。AI 没有拿到完整菜单，不能重新挑选。

`lib/court/recommend.ts:43` 的候选过滤处理价格、类别、不吃辣、不喝饮料；第 78–85 行的评分处理薯条、肉、鸡、辣、营养和省钱。没有“板烧”“雪碧”“麦香鱼”等指定餐品匹配，没有“必须包含”的约束，也没有简称与菜单 ID 的对应关系。写全名“板烧鸡腿堡”仍然失败，说明不只是简称识别问题。

组合主要按类别、份量、价格评分。需求没有进入评分或过滤时，价格更低的通用组合就胜出，因此不同诉求会产生完全相同的推荐。两个备选也继续沿用相同规则，本次指定板烧、雪碧的案例在备选中同样没有这些餐品。

### 2. 否定语义未区分

`lib/court/recommend.ts:78` 只检测输入是否包含“薯条”，命中就给包含薯条的组合加 55 分。“不要薯条”包含相同关键词，因此反而强烈推高薯条组合。

该文件第 86–93 行没有为遗漏板烧、雪碧等指定需求生成说明。系统即使完全没满足诉求，也可以给出普通的预算合规理由。

### 3. AI 文案虚构了替换依据

`lib/ai/judge.ts:41` 只把原始诉求和已选组合传入模型；第 64 行明确禁止模型改变推荐结果，但没有要求逐项核验诉求，也没有提供缺货或替换依据字段。第 83–95 行直接合并生成的文案，未进行事实语义核验。

线上原始返回确实出现了以下说法：

> “然因系统库存逻辑限制，雪碧被替换为纯悦”
>
> “在缺乏板烧现货的情况下，以龙焰鸡腿堡顶替”
>
> “诉求‘汉堡和可乐’获支持（可乐变纯悦）”

这些说法没有上游证据支持，且与菜单可选项或实际命中情况矛盾。接口只执行推荐，没有下单，判词中仍出现“总单已出”“既已上桌”等情节。法庭人设让文案倾向于强行驳回诉求，放大了推荐错误。

### 4. 上诉没有修复点名需求

对原组合提交“我明确要板烧鸡腿堡和雪碧，不要其他汉堡和纯悦”，实际返回麦香鸡＋脆薯饼＋纯悦，33 元。

`app/api/appeal/route.ts:27` 只是把上诉理由拼回原始文本，再调用同一规则引擎；只对“太贵”“不够饱”提供专门限制，其余诉求主要是排除旧组合。它会换餐，却不能确保换成用户指定的餐品。

## 现有检查与验证边界

运行 `npm test -- tests/unit/combinations.test.ts tests/unit/ai-judge.test.ts tests/unit/appeal.test.ts`，3 个文件、17 项测试全部通过。它们覆盖组合、预算、薯条、AI 事实字段保留和部分上诉行为，没有覆盖本次指定品牌饮料、指定汉堡、否定与“只要”语义。测试通过不能证明自由陈述匹配正确。

浏览器表单确认可以输入完整诉求，但本地浏览器提交出现 `TypeError: Failed to fetch`，页面停在等待；浏览器打开线上地址另遇到 `net::ERR_ABORTED`。因此不声称页面最终渲染验证通过。本报告的选餐结论基于实际成功的线上接口、本地接口、MCP 菜单和规则执行；线上接口通过 curl 完成。

本次没有修改业务代码，没有创建订单、提交支付、提交或推送代码。

## 建议修复顺序

1. 在组合引擎前解析明确要求、拒绝项、仅要项和软偏好，并匹配当前菜单的真实 ID；支持“板烧”等简称。
2. 先满足明确包含与排除约束，再按预算、份量和价格优化；不能满足时返回具体缺项与原因，不静默替换。
3. 首次推荐、备选和上诉共用同一套约束与结果校验。
4. AI 只使用明确提供的满足情况和限制生成判词，禁止编造缺货、已下单或用户已接受替换。
5. 将本报告的正向、否定、仅要、多项同时要求和预算不足案例补为回归测试，再实测线上。
